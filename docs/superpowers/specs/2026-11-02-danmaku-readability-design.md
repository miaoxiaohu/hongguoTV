# 弹幕可读性与排布（2026-11-02）

## 要解决什么

用户反馈两条：**「看不清 / 读不完」** 和 **「挡画面 / 摆得乱」**。

2026-11-01 已经把横向几何钉死（第一个字从右缘露头、最后一个字在左缘收尾，飞行区间是整屏），
竖向旋钮（字号/行数/密度/透明度）也都在。这一次动的是**速度模型**和**轨道分配**，
以及一个至今没人注意到的结构性问题：**同屏上限和轨道数是脱节的**。

## 现状与根因

### 1. 速度写死 8 秒 → 长句读不完

`DanmakuOverlay.LIFETIME_MS = 8_000`，**所有弹幕共用一个时长**。
飞行距离是 `屏宽 + 文字宽`，于是 20 个字的长句和 4 个字的短句**视觉速度一样快** ——
长句反而最来不及读。这是「看不清 / 读不完」的第一来源。

### 2. 轨道分配只挑「第一条空轨道」→ 全堆在最上面

`DanmakuTimeline` 里：

```kotlin
var chosen = -1
for (t in freeAt.indices) if (freeAt[t] <= at) { chosen = t; break }
```

永远从第 0 条轨道开始找 → 先来后到的顺序决定位置 → 弹幕成堆落在最上面两三行，
下面 58% 的屏幕永远空着。看着就是「挤在上面、摆得乱」。

### 3. 轨道被「整段独占」→ 密度档位白给，且默认设置下必然叠字

现在一条轨道要等**整条弹幕完全飞出屏幕**（8 秒）才能放下一条：

- AUTO 行数在 720 高时只有 **7 条轨道**（`DanmakuLayouts`：字号 26px、行高 39px、上半屏 42% → 302/39 = 7），
  密度默认「中」的同屏上限是 **12 条**。轨道 7 条装 12 条 → 分配时找不到空轨道 →
  执行「挤最早走完的那一条」分支 → **两条弹幕同轨叠字**。
  默认设置下必然叠字 —— AGENTS.md 里「同屏最高 36 条、铺在 7 行轨道上，屏幕上就是一片白字」说的正是这件事。
- 同时，**轨道数（7）成了同屏条数的硬顶**，密度调成「多」（24）在默认行数下完全没用。

## 决定

用户 2026-11-02 拍板：

1. **固定像素速度**：不管几个字，匀速按 px/s 飘；字越多飘的时间自然越长。
2. **铺满可用轨道**：轨道起点轮转，均匀铺开，不再全堆在最上面几行。
3. **尾随入场**：一条轨道等上一条的**尾巴**离开屏幕右缘就能放下一条（水平方向错开，不叠字），
   不再等整条飞完。**同屏上限回到密度档位本身**（12/24），密度旋钮重新有用。
4. **密度 ↔ 字号联动**：密度调高时字号自动降一档。
5. 附加可读性小项：描边加粗、「淡」档描边抬实、超长弹幕截断。
6. **不做**：人脸/关键区域避让、彩色弹幕、顶部/底部弹幕、反向弹幕、字体选择。

## 实现

### core/DanmakuTiming.kt（新增）

固定像素速度的算式，单独放 core 以便测：

```
基准速度   v = bandWidth / 7.5 秒          (1280 宽 → 约 171 px/s)
飞行时长   life = 7.5s × (1 + 文字宽 / bandWidth)
尾巴清场   clear = 7.5s × (文字宽 / bandWidth)
```

- 4 个字（约 104px）：life ≈ 8.1 秒、clear ≈ 0.61 秒。
- 20 个字（约 520px）：life ≈ 10.5 秒、clear ≈ 3.05 秒。
- 速度对所有弹幕一致，长短句不互相打架。
- `clear` 是尾随入场的核心：弹幕飞到「尾巴越过右缘」那一刻，这条轨道就能接下一条。
  推导：x(e) = band − (e/life)×(band+w)，尾巴越过右缘 ⟺ x+w ≤ band ⟺ e ≥ life×w/(band+w)；
  代入 life 后化简就是 `clear = 7.5s × w/band`。
- **量不到宽度时**（core 里没有 `Paint`）：时长按「一条普通弹幕约占屏宽 8%」估算，
  但**轨道释放退回「整段独占」**（`clear = life`，见 `DanmakuTimeline.clearOf`）——
  按 8% 估出来的清场时刻会**低估**真实的尾巴离场时刻（尾巴真正离开右缘是 `life×w/(band+w)`），
  轨道提前释放，长句的尾巴还在屏上就会被后一条追上，同轨叠字。
  宁可让这条兼容路径上的同屏条数由轨道数决定，也不能叠字。
  （2026-11-02 用户拍板。app 层总会量宽度，所以**产品的路径走的是「已量宽度」那条**，
  尾随入场的完整收益不受影响；退回整段独占的只有 `Probe.kt` 与不传宽度的既有单测。）

### core/Danmaku.kt —— `DanmakuTimeline`

1. **每条弹幕有自己的时长**：`Placed` / `Visible` 加 `lifetimeMs`。
   宽度由 app 层量好传进来（core 不碰 Android 的 `Paint`）：
   构造参数加 `bandWidth: Int` 与 `textWidthOf: (Danmaku) -> Float`。
   **向后兼容**：这两个参数可选 —— 不传时全部弹幕仍用统一的 `lifetimeMs`，
   `Probe.kt` 与现有单测（`DanmakuTest` / `DanmakuDensityTest` / `DanmakuAnchorTest`）
   一行都不用改。
2. **轨道起点轮转**：找空轨道时从上次用的轨道往后环形找，不再永远从第 0 条开始。
3. **尾随入场**：每条轨道记的不是「上一条飞完的时刻」，而是**它的尾巴清场的时刻**
   `freeAt[t] = 入场时间 + clear_i`。新弹幕只要 `freeAt[t] <= 入场时间` 就能进这条轨道。
   因为所有弹幕速度相同，尾巴清场之后两条永远不会再撞上 —— 这是「不叠字」的保证。
4. **删掉「挤轨道」分支**：找不到可用轨道就是「等」—— 等到最早有轨道清场为止
   （这一步和「等密度空位」一样受 2 秒上限约束，超了丢）。
5. **同屏上限回到密度档位**：上限就是 `maxOnScreen`（12/24），不再被轨道数卡住。
6. **「还活着」的判定不能再用统一寿命的二分**：寿命不等长 → 存活集合不再是一个连续区间。
   改成：按入场时间升序的列表 + 二分定位「可能还活着」的下界
   （`enterAt > at − 最大时长`），再在这个小区间里线性筛（区间长度受同屏上限约束，很小）。

`DanmakuMotion.xAt` 的公式不用改：`bandWidth − (elapsed/lifetime) × (bandWidth + textWidth)`
在固定速度下正好等价于匀速，只是 lifetime 换成每条自己的。

### core/DanmakuStyle.kt —— `DanmakuLayouts`

- `resolve(heightPx, size, requestedRows, density = DanmakuDensity.MEDIUM)`：密度 `HIGH` 时字号 ×0.85，
  `LOW` 时不放大（放大可能溢出屏幕），`MEDIUM` 不变。用户手选的字号仍是上限。
  `density` 带默认值，现有单测不用改。
- `DanmakuAlpha.LIGHT` 的描边 alpha 160 → **180**（淡档 fill 105，白字在亮画面上要靠黑边撑住）。

### app/DanmakuOverlay.kt

- `setItems` 里先按最终顺序量好每条的宽度（`Paint.measureText`），再交给 `DanmakuTimeline`。
- 绘制时用每条自己的 `lifetimeMs`（`Visible` 里带出来了），不再用全局 8 秒。
- 描边粗细：`strokeWidth` 0.1 → **0.14** 倍字号。
- **超长弹幕**：文字宽超过屏宽 90% 时截断并加「…」，截完重新量宽。

### app 接线

`setStyle` 的签名加 `density`（已有）；字号/密度联动在 `applyLayout()` 里生效，
密度变了要重排（哪些该丢、哪些该晚飘都要重算）—— 现有 `setStyle` 已经会重排。

## 单测

`core/src/test/kotlin/com/hongguotv/core/DanmakuTimingTest.kt`（新增）：

- 文字越宽 → 时长越长，且严格递增。
- 时长与宽度线性一致：两条弹幕的 `life / (1 + w/band)` 相等（同一个 v）。
- 尾巴清场时间与宽度成正比：`clear = 7.5s × w/band`。
- 量不出宽度时，**轨道释放**退回到「整段独占」（`clear = life`）—— 断言放在 `DanmakuTrackTest`
  （它是轨道层的语义，`DanmakuTiming` 只管算式本身）。

`DanmakuTimelineTest`（新增）：

- **同轨两条弹幕不叠字**：同一轨道上，后一条的入场时间 ≥ 前一条的尾巴清场时刻。
- **长句确实飘得更久**：宽度大的那条 `lifetimeMs` 更大。
- **轨道铺开**：N 条弹幕铺到 K 条轨道时，K 条都被用到（不再全在第 0 条）。
- **同屏上限守得住**：任意时刻可见条数 ≤ 密度档位上限（这次是 12/24，不是 7）。

`DanmakuTest` / `DanmakuDensityTest` / `DanmakuAnchorTest`（现有）：

- 全部保持通过（向后兼容：不传 `bandWidth` / `textWidthOf` 时行为不变）。

`DanmakuStyleTest` 扩写：

- 密度 HIGH 时字号比 MEDIUM 小；LOW 时不放大。
- 行数/钳制逻辑不变（原有断言全部保留）。

## 已知取舍

- **速度模型一改，今天「8 秒」的观感就变了**：今天所有弹幕一律 8.0 秒（写死的），
  改成固定像素速度后短句约 8.1 秒、长句约 10.5 秒 —— 长句明显变慢变久。这是刻意的 ——
  长句读不完比短句慢一点更难受。
- **轨道轮转会让弹幕位置不如现在「整齐」**：现在是「第一条空轨道」，视觉上像表格；
  轮转后更均匀但没有固定规律。用户选了「铺满」，这一条跟着变。
- **尾随入场意味着同一条轨道上可能同时有两条弹幕**（水平错开，视觉上不叠字）。
  同屏条数因此回到密度档位：默认「中」= 12 条（以前被轨道数卡在 7 条）。
  代价是屏幕上文字总量变多 —— 「挡画面」这一项由密度旋钮和字号联动来管。
- **尾随入场对长句更严格**：长句的尾巴清场要 3 秒（520 字宽），所以长句之间的间隔更大，
  爆发时段里长句更容易被「等不到位置」而丢掉。
