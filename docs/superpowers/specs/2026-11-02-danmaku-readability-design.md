# 弹幕可读性与排布（2026-11-02）

## 要解决什么

用户反馈两条：**「看不清 / 读不完」** 和 **「挡画面 / 摆得乱」**。

2026-11-01 已经把横向几何钉死（第一个字从右缘露头、最后一个字在左缘收尾，飞行区间是整屏），
竖向旋钮（字号/行数/密度/透明度）也都在。这一次动的是**速度模型**和**轨道分配**，
以及一个至今没人注意到的结构性问题：**同屏上限和轨道数是脱节的**。

## 现状与根因

### 1. 速度写死 8 秒 → 长句读不完

`DanmakuOverlay.LIFETIME_MS = 8_000`，**所有弹幕共用一个时长**。
飞行距离是 `屏宽 + 文字宽`，于是 20 个字的长句和 4 个字的短句**视觉速度一样快** ——
长句反而最来不及读。这是「看不清 / 读不完」的第一来源。

### 2. 轨道分配只挑「第一条空轨道」→ 全堆在最上面

`DanmakuTimeline` 里：

```kotlin
var chosen = -1
for (t in freeAt.indices) if (freeAt[t] <= at) { chosen = t; break }
```

永远从第 0 条轨道开始找 → 先来后到的顺序决定位置 → 弹幕成堆落在最上面两三行，
下面 58% 的屏幕永远空着。看着就是「挤在上面、摆得乱」。

### 3. 同屏上限 > 轨道数 → 默认设置下必然叠字

| 量 | 值 | 出处 |
|---|---|---|
| AUTO 行数（720 高） | **7 条轨道** | `DanmakuLayouts`：字号 26px、行高 39px、上半屏 42% → 302/39 = 7 |
| 密度「中」的同屏上限 | **12 条** | `DanmakuDensity.MEDIUM` |

轨道 7 条装 12 条 → 分配轨道时找不到空轨道 → 执行「挤最早走完的那一条」分支：

```kotlin
chosen = freeAt.indices.minByOrNull { freeAt[it] } ?: 0   // 硬挤 → 两条同轨叠字
```

**默认设置（AUTO 行数 + 密度「中」）下必然叠字。**
AGENTS.md 记的「同屏最高 36 条、铺在 7 行轨道上，屏幕上就是一片白字」，
说的正是这件事 —— 那 36 条里必然有几条是叠在一起的。

## 决定

用户 2026-11-02 拍板：

1. **固定像素速度**：不管几个字，匀速按 px/s 飘；字越多飘的时间自然越长。
2. **铺满可用轨道**：轨道起点轮转，均匀铺开，不再全堆在最上面几行。
3. **密度 ↔ 字号联动**：密度调高时字号自动降一档。
4. 连带必须一起修：同屏上限受轨道数约束、轨道占用按每条自己的时长算、同屏判定不再用二分。
5. 附加可读性小项：描边加粗、「淡」档描边抬实、超长弹幕截断。
6. **不做**：人脸/关键区域避让、彩色弹幕、顶部/底部弹幕、反向弹幕、字体选择。

## 实现

### core/DanmakuTiming.kt（新增）

固定像素速度的算式，单独放 core 以便测：

```
基准速度   v = bandWidth / 7.5 秒          (1280 宽 → 约 171 px/s)
飞行时长   lifetime = 7.5s × (1 + 文字宽 / bandWidth)
```

- 4 个字（约 104px）：约 8.1 秒 —— 与今天基本一致。
- 20 个字（约 520px）：约 10.5 秒 —— 长句自动多拿 2.5 秒。
- 视觉速度对所有弹幕一致，长短句不互相打架。
- 基准 7.5 秒取自今天「8 秒过屏」的手感，略慢一点点。

### core/Danmaku.kt —— `DanmakuTimeline`

1. **每条弹幕有自己的时长**：`Placed` / `Visible` 加 `lifetimeMs`。
   宽度由 app 层量好传进来（core 不碰 Android 的 `Paint`）：
   构造参数加 `bandWidth: Int` 与 `textWidthOf: (Danmaku) -> Float`。
   **向后兼容**：这两个参数可选 —— 不传时全部弹幕仍用统一的 `lifetimeMs`，
   `Probe.kt` 与现有单测（`DanmakuTest` / `DanmakuDensityTest` / `DanmakuAnchorTest`）
   一行都不用改。
2. **轨道起点轮转**：找空轨道时从上次用的轨道往后环形找，不再永远从第 0 条开始。
3. **有效同屏上限 = `min(密度档位上限, 轨道数)`**：轨道装不下就等位置或丢弃。
4. **删掉「挤轨道」分支**：找不到空轨道 = 该条不排（配合 3，正常情况下不会发生）。
5. **轨道占用按每条自己的结束时间**：`freeAt[t] = at + lifetime_i`。
6. **「还活着」的判定不能再用二分**：寿命不等长 → 存活集合不再是一个连续区间。
   改成：按入场时间升序的列表 + 二分定位「可能还活着」的下界
   （`enterAt > at - 最大时长`），再在这个小区间里线性筛（区间长度受同屏上限约束，很小）。

`DanmakuMotion.xAt` 的公式不用改：`bandWidth - (elapsed/lifetime) × (bandWidth + textWidth)`
在固定速度下正好等价于匀速，只是 lifetime 换成每条自己的。

### core/DanmakuStyle.kt —— `DanmakuLayouts`

- `resolve(heightPx, size, requestedRows, density = DanmakuDensity.MEDIUM)`：密度 `HIGH` 时字号 ×0.85，
  `LOW` 时不放大（放大可能溢出屏幕），`MEDIUM` 不变。用户手选的字号仍是上限。
  `density` 带默认值，现有单测不用改。
- `DanmakuAlpha.LIGHT` 的描边 alpha 160 → **180**（淡档 fill 105，白字在亮画面上要靠黑边撑住）。

### app/DanmakuOverlay.kt

- `setItems` 里先按最终顺序量好每条的宽度（`Paint.measureText`），再交给 `DanmakuTimeline`。
- 描边粗细：`strokeWidth` 0.1 → **0.14** 倍字号。
- **超长弹幕**：文字宽超过屏宽 90% 时截断并加「…」，截完重新量宽。

### app 接线

`setStyle` 的签名加 `density`（已有）；字号/密度联动在 `applyLayout()` 里生效，
密度变了要重排（哪些该丢、哪些该晚飘都要重算）—— 现有 `setStyle` 已经会重排。

## 单测

`core/src/test/kotlin/com/hongguotv/core/DanmakuTimingTest.kt`（新增）：

- 文字越宽 → 时长越长，且严格递增。
- 时长与宽度线性一致：两条弹幕的 `lifetime / (1 + w/band)` 相等（同一个 v）。
- 空宽（量不出来）时退化到基准 7.5 秒。

`DanmakuTimelineTest` 扩写：

- **任意时刻同屏条数 ≤ min(密度档位, 轨道数)**。
- **同一轨道上两条弹幕不重叠**：后一条的入场时间 ≥ 前一条的结束时间。
- 轨道分配覆盖到全部可用轨道（N 条弹幕铺满 K 条轨道，K 条都被用到）。
- 长短句混合时，长句的存活时长确实更长。
- 弹幕不多时一条不少、一根手指都不动。

`DanmakuStyleTest` 扩写：

- 密度 HIGH 时字号比 MEDIUM 小；LOW 时不放大。
- 行数/钳制逻辑不变（原有断言全部保留）。

## 验收

**判据用硬指标，不看图**（沿用 2026-11-01 的规矩）：

1. `:core:test` 全绿。
2. `-dbg` 合成弹幕包在 Palm 上录屏，逐帧量像素：
   - 一条长弹幕与一条短弹幕的**移动速度相同**（同屏宽差值 / 时间差一致）；
   - 同一轨道上两条弹幕的亮像素**不重叠**；
   - 弹幕横向分布覆盖到所有可用轨道（不是全在顶部两行）。
3. 实机走一遍设置页：密度切「多」时字号确实变小（回读 `native-library-v1` 与摘要文案一致）。
4. **正式交付包必须撤掉 `-dbg` 探针**（AGENTS.md：诊断代码只允许活在临时包里），
   撤完重新出包、重新装一次。
5. 测完 `adb shell am force-stop com.hongguotv.nativeapp`。

## 已知取舍

- **速度模型一改，今天「8 秒」的观感就变了**：今天所有弹幕一律 8.0 秒（写死的），
  改成固定像素速度后短句约 8.1 秒、长句约 10.5 秒 —— 长句明显变慢变久。这是刻意的 ——
  长句读不完比短句慢一点更难受。
- **轨道轮转会让弹幕位置不如现在「整齐」**：现在是「第一条空轨道」，视觉上像表格；
  轮转后更均匀但没有固定规律。用户选了「铺满」，这一条跟着变。
- **有效同屏上限变成 `min(密度, 轨道数)`**：默认档（AUTO 7 轨 + 密度「中」12）实际同屏上限
  从 12 降到 **7**。密度「中」在 AUTO 行数下实际只飘 7 条 —— 这是「不叠字」的代价，
  用户若想要更多条，必须自己把行数调上去（12 行 → 上限 12）。
