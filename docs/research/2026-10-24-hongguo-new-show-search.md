# 红果新剧搜不到：实测与修法

实测日期：2026-10-24。触发事件：用户反馈搜不到当天上架的新剧《我刚穿越，校花竟是重生女帝》。

## 结论

**站方一直有这部剧，是 App 的搜索够不到它。** 搜索只有两条路，两条都够不到：

1. **本机索引**：走查站方三条分类目录得到的快照，**7 天**才重建一次（`CatalogueIndexDisk.MAX_AGE`）。
   电视上那份是 10 月 22 日左右建的 —— 这部剧当天才上架，索引里没有。
2. **站方搜索结果那 10 行**（`/api/search/result?query=`）：站方是模糊排序 + 固定十条同类热门，
   **只有输入完整剧名时才命中**。用半截词查，翻完 22 页（220 行）也不出现。

修法：给搜索补一条**按剧名排**的路 —— 站方的联想建议 `/api/search/suggestion/?query=`，
同样的半截词，它把这部剧排在**第一行**。

## 这部剧是什么样的一部电影

| 项 | 值 |
| --- | --- |
| 剧名 | 我刚穿越，校花竟是重生女帝 |
| `series_id` | `7699683154444946457` |
| 集数 | 322 |
| `create_time` | 1792722184（2026-10-24 当天） |
| 标签 | 玄幻 · 穿越 · 系统 · 重生 · 都市 |
| 热度 | 4656 万 |

- **站方搜索结果**：输完整剧名 → **第 1 行**。
- **站方目录**：在**漫剧（`comic-drama`）第 15 页**。不在真人剧目录，也不在 AI 剧目录。
- **站方 sitemap**：**不在**（29 个子文件全扫过，没有这个 id）。

## 两条路的实测差别（2026-10-24）

同一个词，问两个接口：

| 关键词 | `/api/search/result` | `/api/search/suggestion/` |
| --- | --- | --- |
| 我刚穿越，校花竟是重生女帝 | **第 1 行命中** | **第 1 行命中** |
| 我刚穿越 | 翻完 22 页**没有** | **第 1 行命中** |
| 校花竟是重生女帝 | 翻完 22 页**没有** | **第 1 行命中** |

原因：搜索结果那条路按**热度**排，新剧的权重还没起来，输半截词时被同类热门挤掉；
联想建议那条路按**剧名**排，半截词就能落到它头上。

## 联想建议的返回形状

顶层只有 `suggestionList`。每行有一个 `word_type`，剧 id 藏在不同的地方：

| `word_type` | 剧 id 在哪 | 能不能进列表 |
| --- | --- | --- |
| `short_play_name` | `video_data.series_id` | **能**，前提是 video_data 齐全 |
| `short_play_name`（video_data 空） | `keyword` | **不能**（见下） |
| `title` | `keyword` | **不能** —— 那是**另一部剧**的 id |
| `common_query` / `category` / `short_play_actor` | 没有剧 id | 不能 |

`short_play_name` + video_data 齐全的行给的是完整信息：`series_id`、`series_title`、`episode_cnt`、
`series_intro`、`series_cover`、`episode_right_text`、`category_list`（标签）、`hot_score_data`。

### video_data 空着的那一行是死的

同一个词的建议里第二行是「我刚穿越，校花竟是重生女帝第二季」（id `7699791879176473662`），
它的 `video_data` 是空的。**这个 id 的详情页回 404。**

```
GET /detail?series_id=7699791879176473662  →  HTTP 404
GET /detail?series_id=7699683154444946457  →  HTTP 200，vid_list 322 项
```

这正是 2026-10-23 那份研究里记的「同标题两个条目：其中一条是死的」。
所以只收 `word_type=short_play_name` **且 video_data 里有 episode_cnt** 的行。

## 走过的两条死路

### 一、目录页不是按上架时间排的 —— 只补第一页救不了

新剧落在 `comic-drama` **第 15 页**，而第 1 页的头几部是别的剧。目录的顺序是站方自己的
（不是按 `create_time`，也不是新到旧）。所以「新剧上架 → 刷新目录第一页」这种省事的做法
**抓不到它**。目录不按时间排这件事本身是用 `create_time` 对比第 1 页和第 15 页确认的
（页面 HTML 里没有 `create_time` 字段，只能从搜索结果里取）。

### 二、sitemap 不能用

- `https://hongguoduanju.com/sitemap.xml` → 29 个子 sitemap，`lastmod` 是当天。
- 29 个子文件加起来约 **150 MB**，单个 5 MB，里面大半是 `/player/{video_id}` 的**剧集**地址。
- 扫完 29 个文件，**没有**这个剧的 id —— sitemap 落后于目录。

一晚上拉 150 MB 的 XML 只为了知道「站上新了什么」，在 J1900 上不现实，而且它连这部新剧都没有。

## 改了什么

`ContentRepository`：

- 新增 `siteRows(keyword, askSuggestion)`：搜索结果那条路照旧，**索引没答上来时**再问一次联想建议。
- 新增 `suggestionSearch(keyword)`：只收 `short_play_name` 且 `episode_cnt > 0` 的行。
- 两条路各坏各的：只坏一条时**不算**「站方不可用」（手上还有站方的行）；
  两条都空才算，错误分类沿用原来的 `ServerSearchProblem`。
- 索引没答上来时，命中的行排**在同类推荐前面** —— 排在十条不相干的剧后面就等于没有。

只在索引没答上来时问联想建议：索引答上来时页面上已经有三十条本机索引的结果，
再多问一次只是多一个请求；而索引答不上来，正是「站上新剧还没被走查收进去」的时候。

`CatalogueIndexDisk.MAX_AGE`：**7 天 → 1 天**（`CatalogueIndex.kt`）。

站方天天上新，一份放一周的索引就是一周 behind —— 这部当天上架的剧在旧索引里根本没有。
重建是 102 个串行请求，跑在正在被使用的那份索引背后，用户看不见代价；
走查被打断时从断点接着走，不是从头再来。

## 还没解决的

- **「更新索引」按钮只在索引过期或没建完时出现**（`MainActivity.kt` 里
  `!isCatalogueComplete() || isCatalogueStale()`）。过期窗口改成一天之后，这个按钮一天会出现一次 ——
  但索引还新鲜的时候（刚重建完的 24 小时内）用户仍然按不出来。
- 建议接口的第二季那一行是死的（404），现在被过滤掉了 —— 站方把这一部剧的续作做成了另一部
  剧的条目，这一条 App 够不着，除非以后单独拉它的详情页验证。
- 索引的容量上限是 4000 部 / 1.5 MB JSON（`decode` 里 `rows.length() in 1..4000`）。现在 2400 部，
  站方再上一千五百部，索引就会因为读不出来而被整个丢掉。

## 本次用到的探针

`kotlin-tv/core` 的 Probe：

```
--search=<关键词>
```

它跑的是 App 真实的 `search()`：先只问站方，再走查全库建索引，再合并出第 1 页。
「搜不到某剧」只有跑一遍真实路径才能判 —— 站方对任何词都回十条，看屏幕上和跑代码里一样。
