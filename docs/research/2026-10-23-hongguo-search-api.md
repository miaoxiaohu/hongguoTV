# 红果搜索接口实测

实测日期：2026-10-23。手段：Python 直连站方接口做压力与形状验证，`kotlin-tv/core` 的 Probe 走出货代码（`--search=` / `--appsearch` / `--play=` / `--stream=`）核对真实行为。

## 结论

**站方有两个能用的搜索接口，但它们给的不是同一批东西，而其中一个（`suggestion`）指向的多半是别的剧。**

- `/api/search/result` —— 搜索结果，10 条一页，能翻页，但翻页出来的是**噪声**（每页真正命中的只有 0~2 条）。**参数名是 `query`，不是 `keyword`**（用 `keyword` 回 400）。**只收 30 个字**，超了回 400 `invalid_query`，是拒绝不是故障。
- `/api/search/suggestion/` —— 联想建议，字段形状完全不同，里面混着六种 `word_type`，**剧 id 有时在 `keyword` 里，有时在 `video_data.series_id` 里，还有时候根本没有剧 id**。

App 现在的搜索主体是本机索引（2400 部，走查三条分类目录拼出来的），站方那十条只是**补位**。所以这一轮调研要回答的是：站方那一路还值不值得多问一次。

**答案是：不值得。** 原因见下面「同标题两个条目」——它加进来的条目，有一条是**死的**。

## 接口清单

| 接口 | 参数 | 返回 | 实测状态 |
| --- | --- | --- | --- |
| `GET /api/search/result` | `query`（必需）、`page`（可选） | `searchList[].video_data.*`、`pageNum`、`totalPages`、`totalCount`、`hasMore` | 200，约 1% 的 502 |
| `GET /api/search/suggestion/` | `query` | `suggestionList[].{name, keyword, word_type, display_words, video_data}` | 200，样本内 0 失败 |

两者都有 **30 个字**的硬上限。签名 App 接口 `reading/bookapi/search/tab/v/` 仍然是死的：GET / POST 都回 **0 字节**，而同一进程里的对照接口 `video_model/v1/` 回 23 KB `code=0`（实测 2026-10-23）。所以走官网这条路是对的路。

## word_type 与剧 id 藏在哪

这是最容易踩的地方 —— 同一个接口里，剧 id 藏在三个不同的地方：

| `word_type` | 剧 id 在哪 | 备注 |
| --- | --- | --- |
| `short_play_name` | `video_data.series_id` | 有时为空，这时在 `keyword` 里 |
| `title` | **`keyword`** | `video_data` 是空的 `{}` |
| `common_query` | 没有剧 id | `keyword` 是不透明的 query_id（如 `10_1a27842a…`） |
| `category` / `short_play_category` | 没有剧 id | `keyword` 是 category_id |
| `short_play_actor` | `keyword` 是**演员**的 id | 不是剧的 id |

App 现有的 `card()` 只认 `video_data` —— 直接喂 `suggestion` 的数据会**丢掉 `word_type=title` 的全部条目**。

## 长度门槛：30 个字

```
GET /api/search/result?query=<40 个字>
→ 400 {"code":"invalid_query","message":"Provide one non-empty search query of at most 30 characters."}
```

- 空关键词同样回 400
- 这是**拒绝**，不是故障：等下去不会变，重试也没用
- 客户端原来允许 80 个字，所以长关键词**必然**失败

**截断到 30 个字能救回来**（实测）：

| 发的 | 结果 |
| --- | --- |
| 40 字原样 | 400 `invalid_query` |
| 截到 30 字 | 200，10 条，且命中目标剧《我在末世打脸女主了》(`7669833984855002137`) |

所以 0.9.52 把问站方的那一句截到 30 个字，并且**把这个截断说明给用户看** —— 用户打了四十个字，拿到的却是按三十个字问出来的结果。

## 翻页是噪声，不是命中

`query=总裁`：`totalCount=96`、`totalPages=10`，每页 10 条。按「剧名真的含这个词」数：

| 页 | 10 条里真正含「总裁」的 |
| --- | --- |
| page 1 | 2 |
| page 2 | **0** |
| page 3 | 1 |

站方是**模糊排序、固定十条**，不是过滤器 —— 它对任何词都回十条同类型的热门行，还报一个 100~210 的 `totalCount`。App 里那条「剧名必须真的含这个词」的规则（`ContentRepository.mentions`）就是为这个存在的。

**所以不该加站方翻页**：那是一堆 10% 命中率的噪声，而本机索引能给出全部命中。

## 502 的真实频率

| 测量 | 结果 |
| --- | --- |
| 同一个词 30 次，间隔 0.4 秒 | 200 × 30，失败率 0% |
| 带 `page=2` 12 次，间隔 0.35 秒 | 失败 1 次（8%） |
| 不带 `page` 20 次 + `page=2` 20 次 + `page=3` 20 次，间隔 0.4 秒 | **100/100 全 200** |
| 约两百次请求的合计 | 见到 2 次 502，约 1% |

`502 upstream_unavailable` 是站方的**瞬时**故障，跟翻页、跟关键词都无关。

**所以不该加重试**：一次失败只影响那十条补位行，搜索的主体是本机索引，本来就降级安全。为了百分之一的瞬时抖动给每次搜索加一次重试，不值。

## 两个接口给的是不同的集

同一个词「苟王」：

- `/api/search/result` 给 10 条，#4 是 `7692443906679507993`
- `/api/search/suggestion/` 给 8 条候选，**里面没有** `7692443906679507993`

**suggestion 不能当 result 的等价备份** —— 它给的是另一批剧。它对索引覆盖不到的剧确实有用（实测 `query=回到心跳开始时` 给出了 `7697172143917779992 回到心跳开始时`，正是 0.9.51 发布说明里点名的那部索引外的剧），但它是**互补**的，不是**冗余**的。

## 同标题两个条目：其中一条是死的

站方在 `result` 和 `suggestion` 里对同一部剧给了两个不同的 `series_id`。查下去发现它们是**两部不同的剧**：

| | `7692443906679507993` | `7647159490281737278` |
| --- | --- | --- |
| 标题 | 亲姐是末世女主**,**我才是苟王 | 亲姐是末世女主**？**我才是苟王**！** |
| 集数 | 126 | 341 |
| 简介 | 寒潮突降，姐姐是带前世记忆的天选女主 | 姜萤，专属血包，无 CP，偏求生日常向 |
| 标签 | 末世·系统·囤物资·求生·都市 | 科幻末世·无CP·天灾·囤物资 |
| `vid_list` | 126 项，`7692478…` 开头 | 341 项，`7647159…` → `7690865…` |
| 两条 `vid_list` 的交集 | **0** | **0** |
| 在站方分类目录里 | **不在** | **不在** |
| 在站方 sitemap 里 | **在**（`index20.xml` / `index21.xml`） | **不在** |
| 首集（签名接口） | **1080P 播成功**，读 1 MiB 正常 | **HTTP 500** |
| 末集（签名接口） | **1080P 播成功** | **404** → App 报「该来源每部剧只提供前 3 集」 |
| 首集（公开播放页） | 200，有 `contentUrl` | 200，但**没有** `contentUrl`/`main_url` |

两条都不在分类目录里，所以本机索引两个都没有 —— 只有站方搜索够得到它们。

而 `suggestion` 点名的那条（341 集）**一集都播不了**：签名接口回 500，公开播放页没有播放地址，sitemap 里也没有它。它是一条**死条目** —— 详情页、简介、341 个分集 id 都齐全，看着像一部剧。

抽样 30 部（总裁 / 末世 / 修仙 各取首页 10 条）里另有 1 例同样的结构：《天灾末世，她囤满物资后所向披靡！》536 集 ↔ 另一条 id。**频率约 3%。**

## 对 App 的影响与决定

**`suggestion` 不接。** 理由：

1. 它加进来的条目指向**别的剧**，不是同一部剧的另一半 —— 前提就错了。
2. 唯一查过的那条是**死的**。接进来就是往列表里塞一部点开就报错的剧，正是 `mentions` 那条规则要挡掉的「笃定的错答案」。
3. 成本也不小：每次搜索多一个请求、多一个 id 命名空间混杂的解析器、返回的行没有封面和集数（还得再拉详情）。

**站方翻页不接**，**重试也不接** —— 上两节都有数据。

**要接的是**：把问站方的那一句截到 30 个字（实测能救回目标剧）、本机索引多认「剧名在这串字的开头」这种形状、以及把站方的两种失败分开说。
