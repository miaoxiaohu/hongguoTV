# Kotlin 0.9.97：放不了下一集的根因修掉了

<!-- notes -->
一、「有时候放不了下一集」的真正原因找到了：不是地址过期，是**每切一集就换一个设备身份去换地址**，
而站方发下来的号有一半是坏的 —— 坏号对哪一集都只会回一个空答复，那一集就永远取不到地址。
正好是「有时候」。这一版改成同一个身份一直用着，只有它连续几问都空才丢掉换一个，
顺带也把「连看几十集会把站方的发号配额打爆、第 30 集起被拒 10 分钟」这件事一起解决了。
二、还有一类剧集天生只给「字节家的 ByteVC2」编码，电视解不了 —— 备用地址上带着站方两个
「只给改良版」的参数，去掉这两个参数再问，站方就改给电视能解的 ByteVC1 了。
<!-- /notes -->

最低 Android 8.0 / API 26，versionCode 9097。单 APK，安装后联网使用，无需额外服务。沿用发布签名，可覆盖安装 0.9.96 及更早版本并保留本机收藏、观看记录和设置。

## 现象

用户报的是「**视频有时候会失效，放不了下一集**」。

「有时候」这三个字是关键：不是每一集都挂，也不是从头到尾都挂，而是随机地某几集取不到地址。
上一版（0.9.96）修的是「站方按请求随机软拦截取址接口」，改完确实好了一些，但用户还是会遇到。

## 根因（一）：每集换身份 = 每集有大约一半的概率踩到坏号

### 一、站方发的号有一半是坏的

注册接口返回的 `device_id` / `install_id` / `device_token`，好号和坏号**长得一模一样**，
注册响应里没有任何字段能看出这个号好不好。只有拿号去取址才知道。

2026-11-15 实测：注册 6 个新号，每个号拿**同一集**连问 3 次：

| 号 | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| 1 | OK | OK | OK |
| 2 | 空 | 空 | 空 |
| 3 | OK | OK | OK |
| 4 | 空 | 空 | 空 |
| 5 | OK | OK | OK |
| 6 | 空 | 空 | 空 |

**每个号内部三次结果完全一致，号与号之间好坏交替** —— 这不是「按请求随机拦截」，
这是**号级**的：一个号要么一直能用，要么一直不能用。

坏号也不会自己变好：坏号隔 30 秒再问，还是全空；好号隔 30 秒再问，还是全通。

### 二、老代码每集换一个身份，等于每集抛一次硬币

0.9.96 之前的代码是「每取一集就注册一个新身份」（`takePlaybackIdentity()`）。
既然号有一半是坏的，那每集就有大约 **50%** 的概率抽到坏号 —— 那一集永远取不到地址，
落到公开页、只有 10 秒试看片，然后报「播放失败」。

**这就是用户说的「有时候放不了下一集」。**

### 三、换个号会把站方的发号配额打爆

而且每集换身份还有一个更硬的后果：站方对同一台设备发号有配额。
实测连打 60 集时，**第 30 集起注册就被拒**，退避 10 分钟 —— 表现同样是「放不了下一集」，
而且这 10 分钟内谁都救不了。

### 四、这一版怎么改

- **身份跨集复用**：好号要一直用着，别浪费站方的发号配额。
  实测同一个身份连取 **60 集全部成功**。
- **同一个身份最多问 2 次**（间隔 500ms）：只问一次太急（万一只是被拦了一下就把好号丢了），
  问三次没有意义（坏号是永久坏的）。
- **整轮都空才换号**：最多换 8 个身份（`PLAYBACK_TAB_MAX_IDENTITIES`）。
  八个全是坏号的概率约 0.4%，正常情况下第一个号就是好的（平均只注册一次）。
- **身份有寿命**：`PLAYBACK_IDENTITY_MAX_AGE_MS = 2 小时`，过了换一个 ——
  站方可能慢慢地不看它了。
- **老的那条 POST 门**（`signedPlaybackWithFreshIdentity`）同样改成
  「先用手上这个身份问，空答才丢掉换一个」。那个方法名字里带着 "Fresh"，语义已经不成立了，
  改名为 `signedPlaybackWithIdentity`。

## 根因（二）：某些集的备用地址只给 ByteVC2（电视解不了）

### 一、现象

有一类剧集（实测：短剧《修仙满级回现代，我让全家横着走！》第 40 集，
`7703417207283272728`）取址时，5 个清晰度档位（360p~1080p）**全是 `bytevc2`** ——
那是字节家的私有编码，电视的硬解解不了，于是「可播档位 = 0」。

### 二、为什么

备用地址（`fallback_api`）的原始 URL 上带着站方两个「vcube 改良」的参数：

    encode_user_tag=only_roi_vcube_improve_1
    force_fids=...

站方照着这两个参数，**只给字节家的 ByteVC2**。

### 三、实测：去掉这两个参数就能拿到 ByteVC1

对同一集逐个试：

| 试法 | 结果 |
| --- | --- |
| 原样 | 5 个档位全 bytevc2，可播 0 |
| `codec_type` 换成 0/1/2/3/4/5/bytevc1/hevc / 不带 | **每次都还是 bytevc2**，可播 0 |
| 只去掉 `force_fids` | 仍 bytevc2 |
| 只去掉 `encode_user_tag` | 仍 bytevc2 |
| **两个一起去掉** | **4 个档位（360p~1080p）全是 bytevc1，可播 4** |

对照集（`7703417207753018392`）上则是「只去掉 `encode_user_tag`」就够 —— 但两个一起去掉总是有效的。

这两个参数**不是签名的一部分**（备用地址的 `auth_policy` 只有 `{"vs":3,"uid":"0"}`），
去掉之后地址照样有效。

### 四、这一版怎么改

`episodeStream()` 的兜底从两级变成三级：

1. 内联 `video_list` 里有可播档位 → 直接用；
2. 原样问备用地址；
3. 备用地址加 `codec_type=3` 再问；
4. **去掉 `encode_user_tag` 与 `force_fids` 再问**（新增）→ 拿到 ByteVC1。

## 落点

- `core/src/main/kotlin/com/hongguotv/core/ContentRepository.kt`：
  - `tabVideoModel()`：身份跨集复用；每号 2 次尝试（间隔 500ms）；整轮空答才换号；最多 8 个号；
  - `playbackIdentity()`：身份寿命 2 小时，超时换新；
  - 新增 `dropPlaybackIdentity()`（@Synchronized），删掉 `takePlaybackIdentity()`；
  - `signedPlaybackWithFreshIdentity()` → `signedPlaybackWithIdentity()`：老门也改成先复用、空答才换；
  - `episodeStream()`：新增第三级兜底（去 vcube 标记）；
  - 新增 `fallbackWithoutVcubeTags()`：两个参数一起去掉；
  - `addressCache` 的读写加锁（`addressLock`）：播放线程和预取线程并发读写
    `LinkedHashMap`，会损坏内部结构，表现是随机的「刚存进去的地址又找不到了」。
- `core/src/test/kotlin/com/hongguotv/core/ContentRepositoryTest.kt`：
  - 新增 `theFallbackIsAskedAgainWithoutTheVcubeTagsWhenOnlyByteVC2ComesBack`：
    模型内联 bytevc2 + 备用地址带两个标记，站方对带标记的请求回 bytevc2、
    对去掉标记的请求回 bytevc1 —— 断言结果是 `1080P`、URL 以 `PLAIN_HOST` 开头、
    两次备用地址请求都发生过。
  - 补齐了身份复用/换号这条链路的单测。

其余一个字没动：弹幕几何、焦点落点、取址签名本身（六头真签名、query 编码、device_level=1）、
预取策略、HUD 显隐规则都原样保留。

## 版本号说明

- versionCode 由 CI 从 tag 算（`major*1000000 + minor*1000 + patch`）：tag `kotlin-v0.9.97` → 9097。
- 上一版已发布的是 `kotlin-v0.9.96`（9096），新 tag 必须严格新于所有已发布的 kotlin-v 版本。

## 已知限制

- **身份有寿命，但换号仍要花配额**：只有整轮空答才会换号，正常情况下一集一次注册都不多花。
- **ByteVC2 兜底只覆盖站方用这两个参数标记的情况**：如果站方以后改成别的标记方式，
  还得再测一轮 —— 但这一版的兜底不依赖 `codec_type`，不会像以前那样「调参数调不出来」。
